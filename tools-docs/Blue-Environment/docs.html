Blue Environment

Nowoczesne środowisko graficzne dla Waylanda, zbudowane na Tauri i Svelte. Panel, menu Start, centrum sterowania, przełącznik okien, pulpity wirtualne i ponad trzydzieści własnych aplikacji — wszystko w spójnym, szklanym stylu.

WaylandTauri 2SvelteRust16 języków interfejsuEdycja Blue

Wprowadzenie #

Blue Environment to środowisko graficzne znane z edycji Blue systemu HackerOS. Działa jako powłoka pulpitu (panel, launcher, przełącznik okien, powiadomienia) i dostarcza zestaw własnych aplikacji: przeglądarkę, klienta poczty, edytor kodu, menedżer plików, terminal, monitor systemu, menedżer partycji i wiele innych.

Powłoka pulpitu

Panel, menu Start, centrum sterowania, centrum powiadomień, pulpity wirtualne i przełącznik okien.

Własne aplikacje

Ponad 35 aplikacji: od Blue Web i Blue Code po Blue Virt i Blue Security.

Wybór kompozytora

Działa na HackerOS-Comp, labwc, sway i wayfire — wybór w pliku config.hk.

Bezpieczeństwo

Blokada wzorem lub odciskiem palca, kontrola rodzicielska, limity czasu i sejf haseł.

Personalizacja

Motywy powłoki, schematy kolorów, własne motywy i wtyczki w piaskownicy.

Wiele dystrybucji

Pakiety dla Debiana/Ubuntu, Fedory, Arch, Alpine, openSUSE, Gentoo, Void i Nix.

Wersja

Ta dokumentacja opisuje Blue Environment 0.8.0.

Architektura #

Blue Environment składa się z frontendu w Svelte + TypeScript (Vite, Tailwind CSS) osadzonego w powłoce Tauri 2 oraz backendu w Rust. Interfejs komunikuje się z systemem przez mostek IPC Tauri.

WarstwaZawartość
src/frontend Svelte: komponenty powłoki (TopBar, StartMenu, ControlCenter, NotificationCenter, WorkspaceSwitcher…), aplikacje, store’y (okna, motywy, język, skróty), tłumaczenia
src-tauri/backend Rust: komendy Tauri, skaner plików .desktop, śledzenie okien, pogoda, kontrola rodzicielska, czas przed ekranem, motywy, integracja z kompozytorami (backend/)
auth/wspólna biblioteka blue-auth: hashowanie wzoru blokady (Argon2id) i status odcisku palca (fprintd)
packaging/szablony pakietów dla wielu dystrybucji
config/plik .desktop oraz wersja

Aplikacje ładowane są leniwie (*Lazy.svelte), a ich logika systemowa mieszka w osobnych modułach Rust (m.in. BlueMessagesApp, BlueConnect, BlueAccounts, BlueVirt, BluePartitionManager).

Wymagania

Debian / Ubuntu / HackerOS
sudo apt install build-essential curl git \
    libssl-dev libgbm-dev libseat-dev libinput-dev \
    libxkbcommon-dev libudev-dev libdrm-dev \

    libayatana-appindicator3-dev librsvg2-dev pkg-config seatd

Potrzebujesz także Node.js 18+, Rusta (stable) oraz Tauri CLI 2. Do trybu bare-metal (DRM/KMS) włącz seatd i dodaj użytkownika do grupy seat.

seatd
sudo systemctl enable --now seatd
sudo usermod -aG seat $USER   # potem wyloguj się i zaloguj

Budowanie powłoki

Terminal
npm install
npm run build:tauri

npm run build:tauri woła tauri build, który sam uruchamia npm run build (sprawdzenie typów przez svelte-check i vite build), a potem buduje binarkę Rust blue-environment.

Uwaga

Nie uruchamiaj ręcznie npm run build przed npm run build:tauri i używaj build:tauri, a nie npm run tauri — inaczej zobaczysz błąd „Unable to find your web assets”.

Tryb deweloperski

Terminal
npm run dev          # serwer Vite na :1420
cargo tauri dev      # albo: npm run tauri -- dev

Ekran blokady #

Ekran blokady (Super+L) obsługuje odblokowanie wzorem (pattern lock) oraz odciskiem palca przez fprintd. Wzór jest zapisywany jako skrót Argon2id — ten sam algorytm co sejf haseł Blue Accounts — a logika jest współdzielona przez bibliotekę blue-auth, więc format nigdy nie rozjedzie się między sesją pulpitu a menedżerem logowania (BEDM).

Konfiguracja: Ustawienia → Bezpieczeństwo lub aplikacja Blue Security and Privacy.

Blue AI #

Wbudowany asystent AI łączy się z wybranym dostawcą przez proxy w backendzie Rust. Obsługiwane serwisy:

ChatGPTClaudeGeminiDeepSeekGrok (xAI)Lokalnie: Ollama

Modele chmurowe wymagają własnego klucza API dostawcy. Tryb lokalny korzysta z Ollamy (np. llama3.2, mistral, codellama, phi3, qwen2.5), więc rozmowy nie opuszczają komputera.

Wtyczki #

Wtyczki działają w piaskownicy (PluginRuntime) z jawnie przyznawanymi uprawnieniami: powiadomienia, schowek i prywatny magazyn danych wtyczki. Wbudowana wtyczka Sandbox Demo pokazuje każde z tych uprawnień w działaniu. Wtyczkami zarządzasz w Ustawienia → Wtyczki.

Kompozytory (backendy) #

Blue Environment może działać na czterech kompozytorach. Wybór następuje w sekcji [backend] pliku config.hk (HackerOS Configuration Format):

config.hk
[backend]
-> compositor => wayfire          ! albo: labwc, sway, hackeros-comp (domyślny)
-> generate_wayfire_config => true
-> wayfire_binary => wayfire

Dla backendów labwc, sway i wayfire dostępne są ustawienia <nazwa>_binary, <nazwa>_args, <nazwa>_config_dir i generate_<nazwa>_config — czytane są tylko te aktywnego kompozytora.

Który plik konfiguracyjny?

Używany jest istniejący config.hk, w kolejności: $BLUE_CONFIG_HK, $XDG_CONFIG_HOME/Blue-Environment/, ~/.config/Blue-Environment/, /etc/xdg/Blue-Environment/. Jeśli żadnego nie ma, tworzony jest domyślny w ~/.config/Blue-Environment/config.hk.

Start systemu

compositorCo się dzieje
hackeros-compbinarka działa jako powłoka, bez zmian
labwc / sway / wayfirebrakująca konfiguracja jest generowana (bez nadpisywania istniejącej), po czym Blue uruchamia wybrany kompozytor, który startuje powłokę. HackerOS-Comp nie jest wymagany
wybrany kompozytor niezainstalowanyostrzeżenie i zachowanie klasyczne

Jeśli sesja graficzna już istnieje, kompozytor nie jest zagnieżdżany (wymusisz to opcją --start-backend). --no-backend zawsze uruchamia samą powłokę, a --backend-info wypisuje wykryte informacje.

Co jest wspólne dla labwc, sway i wayfire

  • lista okien, fokus, minimalizacja, maksymalizacja i zamykanie każdego okna natywnego i XWayland (protokół wlr-foreign-toplevel-management);
  • systemowa historia schowka, także z zewnętrznych aplikacji (wl-paste --watch, pakiet wl-clipboard);
  • skróty globalne przy fokusie na aplikacji natywnej — przez blue-environment --ctl;
  • zrzuty ekranu przez grim, blokada, przeładowanie konfiguracji i liczba pulpitów — tłumaczone na mechanizm danego kompozytora;
  • uruchamianie aplikacji natywnych z jawnym środowiskiem sesji (WAYLAND_DISPLAY, DBUS_SESSION_BUS_ADDRESS…), własną sesją (setsid) i logiem w ~/.cache/Blue-Environment/launch.log;
  • Alt+Tab zależy od fokusu: gdy fokus ma powłoka Blue, działa przełącznik Blue (okna Blue i natywne); gdy aplikacja natywna — przełącznik kompozytora.

Co różni backendy

  • Sposób startu powłoki: labwc przyjmuje polecenie startowe w wierszu poleceń (-s); sway i wayfire startują programy tylko z własnej konfiguracji (linia exec / wpis [autostart]), więc Blue dba, by taka linia istniała. Przy istniejącej konfiguracji sway Blue jej nie rusza — generuje osobny plik z include i jedną linią exec; w wayfire dopisuje minimalny wpis [autostart].
  • Format konfiguracji skrótów, motywów i reguł okien — każdy backend ma własny generator (labwc_config, sway_config, wayfire_config). Domyślna konfiguracja sway jest pływająca, a nie kafelkowa.
Znane ograniczenia

Okna Blue żyją w warstwie powłoki, czyli pod oknami natywnymi. Przełączanie pulpitów „na żywo” i DPMS nie mają IPC w sway/wayfire. Wayfire nie ma przeładowania konfiguracji na żywo w tej wersji — zmiany wymagają ponownego logowania. Konfiguracja wayfire była testowana na podstawie dokumentacji wtyczek i testów jednostkowych, bez uruchomienia samego kompozytora.

Rozwiązywanie problemów #

„Unable to find your web assets”

Frontend nie został zbudowany przed tauri build. Użyj zawsze npm run build:tauri — skrypt beforeBuildCommand zbuduje frontend automatycznie.

Błąd uprawnień seatd / seat

Terminal
sudo systemctl enable --now seatd
sudo usermod -aG seat $USER
# następnie wyloguj się i zaloguj ponownie

Błąd cechy chrono

Upewnij się, że w Cargo.toml jest chrono = "0.4" bez dodatkowych cech (cecha local-offset nie istnieje w chrono 0.4.x).

Aplikacja natywna nie startuje

Sprawdź ~/.cache/Blue-Environment/launch.log — trafia tam stderr uruchamianych aplikacji. Jeśli program kończy się błędem tuż po starcie, Blue pokazuje powiadomienie z powodem.

Maszyna wirtualna i VirtualBox

W maszynie wirtualnej Blue wykrywa WAYLAND_DISPLAY / DISPLAY i działa zagnieżdżone; na „gołym” sprzęcie (TTY, brak serwera grafiki) korzysta z trybu DRM/KMS przez libseat, co wymaga działającego seatd.

Status i ograniczenia #

  • Powłoka działa samodzielnie pod dowolnym istniejącym kompozytorem Wayland/X11; własny kompozytor oparty na Smithay (compositor/) jest planowaną architekturą i nie ma go jeszcze w repozytorium.
  • Okna Blue żyją pod oknami natywnymi (warstwa powłoki).
  • Część integracji (m.in. wayfire) wymaga weryfikacji na sprzęcie.

Aktualne informacje o statusie znajdziesz w repozytorium projektu.
